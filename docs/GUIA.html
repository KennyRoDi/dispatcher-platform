Guía para contribuir a dispatcher-platform

Qué se construye, cómo está organizado el repositorio y cómo llevar una feature de la idea a main. II Proyecto Programado de IC-6600, Alternativa B. Entrega: 10/nov/26.

1. Qué es el proyecto

Una plataforma distribuida que recibe casos de análisis con conversaciones, notas de voz, imágenes, videos y documentos, los reparte entre workers especializados en al menos tres nodos y genera reportes con evidencias enlazadas a su fuente.

El análisis es la carga de trabajo, no el objetivo. Se evalúa cómo el sistema administra memoria, planificación, E/S y seguridad, y que eso se demuestre con datos medidos. No se entrenan modelos.

2. Primer día

Necesitas Python 3.13 o superior, Git y GitHub CLI (gh). En Windows, usa py si python no funciona.

  1. Acepta la invitación al repositorio y clónalo. 
    gh auth login
git clone https://github.com/KennyRoDi/dispatcher-platform.git
cd dispatcher-platform
  2. Configura tu identidad real. El autor de tus commits debe coincidir con la matriz de responsabilidades. 
    git config user.name "Tu Nombre"
git config user.email "tu-correo"
  3. Crea el entorno y confirma que las pruebas pasan. 
    python -m venv .venv
source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements-dev.txt
pytest -q -m "not integration and not acceptance"
  4. Identifícate con tu usuario de GitHub y mira tus tareas. 
    python scripts/flujo.py soy tu-usuario
python scripts/flujo.py empezables

Después, en tu agente, ejecuta /empezables y /trabajar F-XX. También puedes hacerlo todo sin agente con los comandos de flujo.py.

Contratos entre módulos

Para no esperar a otros módulos, programa contra los contratos y usa fakes en las pruebas: Priority en src/domain/priority.py, Finding en src/domain/finding.py y los puertos Clock, Analyzer, ObjectStore, WorkQueue y AlertPublisher en src/application/ports.py. Si necesitas cambiar uno, hazlo en una PR y avisa a los módulos afectados.

Regla de capas

infrastructure → adapters → application → domain

Las dependencias apuntan hacia el dominio. src/domain es lógica pura: no importa redis, fastapi, minio ni otras capas. Una prueba lo hace cumplir. El código debe entenderse por sí solo: comenta solo casos borde que el código no pueda expresar.

5. Ciclo de trabajo

Todas las features pasan por las mismas seis fases. Cada fase tiene dos controles: primero la verificación de IA y después tu aprobación. El agente genera todo lo de una fase de una vez, y luego se detiene.

#FaseSe generaEl script exige para aprobarQué debes revisar
1planSPEC.md: alcance, diseño, pruebas y división en PRSin campos …¿Es lo que pide el enunciado? ¿Entiendes el diseño?
2testsPruebas en rojoPruebas nuevas, sin código, y que fallen¿Cubren cada criterio de aceptación?
3implementacionCódigo en verdeCódigo, pruebas en verde, hasta 400 líneas¿Podrías explicarlo y modificarlo sin ayuda?
4verificacionHallazgos de QA y medicionesPruebas en verde, hasta 400 líneas¿Los datos son reales y tienen comando?
5documentacionFichas, documentos, borrador de bitácoraEntrada de la rama en la bitácora¿La bitácora es veraz?
6revisionRevisión del diff contra el SPECTu aprobación¿Aceptas los hallazgos que queden?

Paso a paso

  1. /empezables muestra tus features libres.
  2. /trabajar F-XX crea la rama y el SPEC, y lanza la fase actual.
  3. El orquestador lanza al subagente de la fase, verifica su trabajo y te presenta un informe.
  4. Lees y respondes:
    • «Aprobado»: registra tu aprobación y se detiene.
    • «Aprobado, sigue»: además inicia la siguiente fase.
    • Pides cambios: los aplica, verifica de nuevo y vuelve a preguntar.
    • Hay que volver atrás: flujo.py devolver <fase> "motivo".
  5. Tras aprobar revision, /cierre abre la PR.
  6. Si el SPEC define más partes, /trabajar F-XX abre la siguiente, que repite las fases 2 a 6.
  7. En la última parte, cierre --final marca el fin. Al fusionarla, la feature pasa a hecha.

Tu aprobación es lo que el sistema no puede comprobar. El registro demuestra que se ejecutó aprobar, no que leíste. Si apruebas sin entender, el problema aparecerá en la defensa. Una buena prueba: explica el cambio sin mirar el informe.

aprobar --excepcion "motivo" omite las comprobaciones cuando no aplican, por ejemplo la fase de tests en una feature que solo es documento. Queda registrada y no omite la verificación.

7. Commits, ramas y PR

Conventional Commits, también en títulos de PR

test(F-20): agregar prueba de inanicion con reloj simulado
feat(F-20): ordenar sub-tareas con aging implicito
docs(F-20): agregar ficha de planificacion

Tipos: feat, fix, test, refactor, perf, docs, build, ci, chore, style, revert. Las ramas de feature las crea flujo.py trabajar: feat/F-20-2-scheduler-redis.

PR pequeñas y apiladas

Cada PR hace una sola cosa y tiene hasta 400 líneas, sin contar pruebas ni documentos. El trabajo que depende de otro aún sin fusionar se apila encima, para seguir avanzando sin esperar:

main
 └─ feat/F-20-1-politica-aging        PR 1: base main
     └─ feat/F-20-2-scheduler-redis   PR 2: base la rama de la PR 1
         └─ feat/F-21-1-fifo          PR 3: otra feature encima
  • Revisa y fusiona de abajo hacia arriba. Solo se fusiona lo que va sobre main.
  • Fusiona siempre con python scripts/flujo.py fusionar <numero>.
  • Si cambia una PR intermedia, corrige en su rama y propaga con merge hacia las de arriba.
  • Pide a otra persona que revise. GitHub no lo exige, pero así conoces otro componente, que también te preguntarán en la defensa.

No borres una rama con PR apiladas encima. GitHub cerraría esas PR. El botón «Delete branch» y gh pr merge --delete-branch lo provocan; flujo.py fusionar lo evita.

9. Mediciones y fichas

TDD demuestra que la lógica decide bien. No demuestra cómo se comporta el sistema operativo: eso lo demuestran las mediciones.

  • Con TDD: la decisión de admisión, el orden del scheduler, la cadena de custodia.
  • Con ficha: la memoria real, el OOM real, los MB/s, la captura TLS.

Cada módulo tiene su ficha, docs/modulo-MX-nombre.md, con cinco secciones: qué se implementó, concepto de SO con referencia bibliográfica, método de medición, resultados e interpretación. Los comandos están en docs/IMPLEMENTACION.md §5; los scripts scripts/measure/ están por crear. Los datos crudos van a docs/evidencia/.

Nunca inventes ni estimes un dato como si fuera medido. Si no se pudo medir, se escribe «Pendiente de medir» con su comando. Las mediciones van en los nodos reales y las de M1, en Linux, o se declara la diferencia con WSL2.

10. Bitácora de IA

La IA se puede usar, pero se declara [Parte I §4]. Es el 10 % de la nota. Cada parte registra su entrada en la fase de documentación, y sin ella no se puede abrir la PR.

python scripts/flujo.py bitacora --herramienta "..." --proposito "..." --consulta "..." \
  --resultado "..." --validado "..." --como "comando o prueba" --error-ia "..."
python scripts/flujo.py bitacora --sin-ia

Se publica en la rama estado, para evitar conflictos entre ramas, y se copia a main por PR antes de entregar. Registra errores reales, en especial los que detectes tú: el enunciado pide errores detectados por el equipo.

11. Reglas que no se rompen

  • Datos: solo sintéticos o públicos con licencia. Nada real de terceros, ni siquiera tus chats si incluyen mensajes de otras personas [B.3].
  • Secretos: el repositorio es público. Una llave subida se da por comprometida: hay que revocarla, no basta con borrarla.
  • Historial: fechas reales y commits propios. Nada de simular avance [Parte I §3].
  • Terceros: cita la fuente en el código y en la documentación [Parte I §9].
  • Alcance: lo que el enunciado no pide no entra. Una decisión que no define se registra como SUP-XX.
  • Distribución: tres nodos worker en máquinas separadas [B.2]. Workers nunca como root [B.5 M4].
  • Importaciones: para reutilizar código, copia los archivos y cita el origen, sin traer commits de otros repositorios.
  • Generados: no edites a mano STATUS.md, ni los campos de fase y las aprobaciones del SPEC.
